INDYTEER: CHANGES NEEDED NOW (SUPABASE-ONLY ARCHITECTURE)
=========================================================

Decision: no Node.js API. The React frontend talks directly to Supabase (supabase-js).
Security and business rules live in Postgres (RLS, SQL functions, triggers), Storage policies,
and (only where a privileged key is needed) Supabase Edge Functions.

This replaces Sections 1, 3 and 6 of BACKEND_REQUIREMENTS.txt (Node host, REST route list,
API response/error shape). The schema (Section 2) and business rules (Section 4) still apply.
"G#" refers to the gap list in BACKEND_REQUIREMENTS.txt.

Priority key:  [P0] blocker / security   [P1] required for the frontend to work
               [P2] needed before launch   [P3] cleanup / later

B. SECURITY FIXES IN THE EXISTING MIGRATION  [P0]
================================================================================
RLS is now the ONLY security layer, so these must be fixed before real users:

B1. profiles: users can update their own account_type (volunteer -> organization).
    FIX: remove account_type (and id, created_at) from what users can update. Set account_type
         only through an onboarding RPC that works once (while onboarded = false), or through
         the signup trigger.

B2. applications: a volunteer can INSERT with status = 'accepted' (no restriction on status).
    FIX: remove direct INSERT/UPDATE/DELETE on the registrations table for clients. All
         changes go through RPC functions (section D).

B3. applications: the org UPDATE policy has no WITH CHECK or column limit, so an org could
    rewrite volunteer_id or opportunity_id.
    FIX: same as B2 (RPC only), or a trigger that rejects changes to any column except status.

B4. applications INSERT does not check: opportunity open/published, registration deadline,
    available spots, duplicate after decline/removal.
    FIX: enforce in the register RPC with a row lock on the opportunity (no overbooking).

B5. opportunities: UPDATE/DELETE policies do not require the caller to be an organization
    (org_id = auth.uid() is enough, which is fine) but INSERT/UPDATE need column validation
    (draft vs published completeness, ends after starts, deadline <= date).
    FIX: CHECK constraints (see section C).

B6. profiles are fully public (select using true), which will expose phone, availability and
    privacy-controlled fields once they are added.
    FIX: split public columns from private ones (separate table or a view/RPC). See section C.

B7. Edge-only secrets: the service_role key must never be in the frontend or in VITE_* vars.

Opportunities
 C4. Add/rename columns to match the form:
       category (replaces "cause"), city (replaces "neighborhood"), location (venue name),
       address, virtual, min_age, skills[], hours numeric(4,1), registration_deadline,
       recurrence enum (none/weekly/biweekly/monthly), instructions,
       status enum draft/published (replaces open/closed), spots NOT NULL >= 1.
 C5. Event time storage (Indiana): store event_date (date) + start_time + end_time (local

 C6. CHECK constraints: published rows must be complete; end_time > start_time; deadline <=
     event_date; hours > 0; min_age 1-99.
 C7. Use one shared category list. Today the DB/frontend use different lists
     (CAUSES/NEIGHBORHOODS in src/types/models.ts vs CATEGORIES/INDIANA_CITIES in
     src/lib/constants.ts). Pick the frontend's lists and delete the other.

       status enum: pending, approved, declined, cancelled, removed

     Cancel must be a status change (cancelled), not a DELETE, so re-register and history work.
     Add CHECKs: attended => approved; hours_verified => attended.

Indexes / views

================================================================================
D. DATABASE FUNCTIONS (RPC) AND TRIGGERS  [P1]
================================================================================
Called from the frontend with supabase.rpc(). Each runs in a transaction and enforces the
business rules from BACKEND_REQUIREMENTS.txt Section 4. Clients get NO direct write access to
registrations.

Registration RPCs
 D1.  register_for_opportunity(opportunity_id)
        published, not past, deadline not passed, spots left (lock the opportunity row),
        no duplicate; re-register after cancel resets to pending; declined/removed blocked.
        Creates a notification for the org.
 D2.  cancel_registration(registration_id)       volunteer owner; clears attended/verified.
 D3.  approve_registration / decline_registration / remove_registration(registration_id)
        organization owner only; transition rules per the status table; notify volunteer.
        Approving a declined row re-checks spots.
 D4.  set_attended(registration_id, attended)    approved only; false clears hours_verified.
        Decide G5 (block marking attendance before the event date in production).
 D5.  verify_hours(registration_id, hours) / unverify_hours(registration_id)
        requires attended; hours 0.5-24; notify volunteer.

Profile / onboarding RPCs
 D6.  complete_volunteer_onboarding(...) / complete_org_onboarding(...)
        sets account_type once, creates profile rows, sets onboarded, welcome notification.
 D7.  get_volunteer_profile_for_org(volunteer_id)
        applies privacy (public_profile, show_hours, show_history) and the "has registration"
        rule for contact details.

Stats RPCs / views (replace src/store/selectors.ts logic)
 D8.  volunteer_dashboard()    totals (total/verified/pending/completed), upcoming count.
 D9.  org_overview() and org_analytics()
        total registrations, verified hours, hours to verify, active/completed events,
        attendance rate, unique and returning volunteers, 6-month charts, top events,
        registrations by category.
 D10. org_volunteers(q, sort)  volunteers with approved+attended registrations.
 D11. feed(scope, category, q, cursor)  merged opportunities + posts, newest first.
 D12. recommended_opportunities()  (or keep scoring in the client) [G18].

Triggers
 D13. updated_at on every table with that column.
 D14. starts_at/ends_at from local date/time/timezone (C5).
 D15. Notification on publish (to followers with new_opportunity_notifications on),
      on follow (to org), on registration changes (inside the RPCs).
 D16. Signup trigger (C1).
 D17. Block changes to protected columns (account_type, verified, org_id) via trigger or by
      excluding them from policies.

RLS policy rewrite (after the above)
 D18. Rebuild policies per table:
        public read: published opportunities, organizations, posts
        owner only:  settings, notifications, manual hours, saved, follows (own rows)
        org owner:   own opportunities (insert/update/delete), own posts
        registrations: SELECT for the volunteer and the owning org only; NO client writes
        admin:       verified flag, announcements (is_platform_admin check)
